# Develop

*Reference for maintainers and other scripts' authors*. The repo-wide procedure is in the root [DEVELOP.md](../../DEVELOP.md).

## Build

`string_theory.user.js` is **generated**, not hand-written; never edit it. The members are listed in [`members.txt`](./members.txt). Every member is a self-contained IIFE. The build ([`build.mjs`](./build.mjs)) unions the metadata blocks and concatenates the bodies, each wrapped in two gates:

- **URL gate**: the script's own `@match` / `@include` / `@exclude` / `@noframes`, tested against the page once at load, as a userscript manager does. A script starts only where its standalone copy would, though the bundle's `@match` covers every script's pages.
- **`@run-at` gate**: `document-start` bodies run immediately; `document-end`/idle bodies wait for `DOMContentLoaded`.

**Shared blocks are written once** ([#786](https://github.com/majkinetor/musicbrainz-userscripts/issues/786)). Every member carries its own copy of the [shared blocks](../../DEVELOP.md#shared-blocks) (`// <ST-UI>` …), which was about 1 MB of repeats. [`share.mjs`](./share.mjs) puts each block once at the top of the bundle, as a function that takes `GM_info` and returns the block's names, and gives each member one line in its place, at the start of the function the block was in:

```js
var { mbuToast, mbuLog, … } = __st_UI(GM_info);
```

Each member still gets its own instance: ST-UI reads the member's `GM_info` (help links, log title, edit-note signature) and keeps per-member state, such as the active log window. The build stops when a block isn't self-contained: when it uses one of the member's own names, when the member assigns one of the block's names, or when a name is declared both in the block and around it. A block that uses another block's names gets them as parameters. The standalone scripts keep their inline copies.

```sh
node userscripts/string_theory/build.mjs
```

The pre-commit hook rebuilds it whenever a member (or this folder's `build.mjs` / `share.mjs` / `icon.svg`) is committed, so the bundle never ships stale. Its `@version` is a build stamp (`YYYY.M.D.HHMMSS`), so every rebuild ships as a newer version. The build also writes [`DOCS.md`](./DOCS.md) from the members' READMEs.

## Metadata

`@icon`, `@run-at` and single-valued metadata are the bundle's own; multi-valued ones (`@match`, `@grant`, `@connect`, `@require`, `@resource`) are the union of all members.

## Runtime

The settings title bar uses `mbuCfgHeader`, retaining its icon, name, version and help. A `ResizeObserver` fits its tabs, using a native select when they cannot share one row; the version hides only if the compact header still needs room. Both paths use the existing tab handler; closing the window disconnects the observer. Tab panels share a grid cell, with inactive panels invisible but still reserving space so switching tabs does not resize the window. General fields and About's scripts use container queries for two columns, based on the window's available width. The Installed update row uses the local build metadata and makes no remote request.

- The scripts left out of a page by their own `@match` are named in the console at the *debug* level: `String Theory: not for this page (their own @match) — …`.
- A page Event Horizon shows inside the tab (`<html data-mbu-page>`, [its DEVELOP.md](../event_horizon/DEVELOP.md#the-page-shown)) can be one a member is for while the page the tab loaded wasn't, so a manager never starts it ([#847](https://github.com/majkinetor/musicbrainz-userscripts/issues/847)). A member that follows Event Horizon's page and reads nothing off MusicBrainz's (`FOLLOWS_EH` in `build.mjs`: Art Station, Platform Check, ISRC Scout, Mission Control) starts there, once, the first time such a page shows (`__stLater`). Any other member would read the page the tab loaded, so it stays off. Falcon matches every page, so it runs anyway, and it puts up its icon when `data-mbu-page` changes.
- The command palette is [`palette.js`](./palette.js), written into the bundle after [`settings.js`](./settings.js), in the same scope. Its setting, pins and recent commands are the GM value `string_theory.palette` (`{ on, key: { ctrl, alt, shift, meta, key }, pins, recent, last }`, each command by its id, `last` the text left in the box). The hotkey listens on `window` in the capture phase, top frame only; the `mbu-st-palette` event opens it too. A theme command previews with `__stTheme.preview()`, which saves nothing.
- The on/off list is the GM value `string_theory.off` (folder names). The build wraps each body in a check against it and adds the menu, which goes only in the top frame.
- The launchers' layout is `mbu.cornerFlow` (column or row) and `mbu.cornerSide` (right or left) in MusicBrainz's `localStorage`, read by every script's `mbRestackCorner` ([shared storage](../../DEVELOP.md#shared-storage)).
- All members share **one** userscript-manager storage namespace (one each when installed separately). Each script prefixes its keys, but it's a shared surface.

## External storage

Google Drive is currently backup-only in settings: sync controls are replaced by a limitation message, and the scheduler and non-manual runs decline Google even when automatic sync was previously enabled. The Google journal adapter remains available internally for compatibility, but the UI exposes only backup/import operations for that provider.

[`sync.js`](sync.js) implements Dropbox connection, scheduling and its revision-checked snapshot file, `/string-theory.json`, inside the registered app folder. The app key is public; the flow uses S256 PKCE and offline access, without a client secret. Register **`https://musicbrainz.org/?st-dropbox=callback`** as an exact redirect URI in Dropbox's [App Console](https://www.dropbox.com/developers/apps). The app needs `account_info.read`, `files.metadata.read`, `files.content.read` and `files.content.write`; its console also controls the development/production status and user limit.

The initiating tab saves a short-lived verifier and state in `string_theory.sync.oauth`, excluded from all snapshots. The callback URL already matches the userscript; it starts no bundled member, applies no pending data and runs no automatic sync. It removes the code from the address bar, verifies state and expiry, exchanges the code with the same redirect URI, and stores credentials only after account lookup succeeds. A GM value-change listener delivers `.oauth.result` to the initiating tab; the callback then closes. A failed or superseded connection leaves working credentials intact.

[`providers.js`](providers.js) is a vendored browser bundle of `@usync/drive` and `@usync/oauth2`, pinned in [`package.json`](package.json), with their licenses. All standard providers are included; the settings expose Dropbox and Google Drive. Rebuild after a library update with `pnpm --dir userscripts/string_theory install` and `node userscripts/string_theory/build-providers.mjs`, then rebuild String Theory normally. The ordinary bundle build reads the committed provider file, so it needs no additional dependency installation. The provider code's fetch is scoped to `stSyncFetch`, which uses anonymous GM requests; only Dropbox API hosts and `www.googleapis.com` are allowed. Dropbox's standard provider put overwrites: the adapter instead uses its authenticated request layer with an exact downloaded revision and an upload `update` precondition (`add` for a missing file), retrying conflicts after another read.

[`sync-google.js`](sync-google.js) uses Google's [GIS token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model). Its official `https://accounts.google.com/gsi/client` script loads only when the user selects Google Drive or opens settings with Google selected. Connect calls `requestAccessToken` synchronously from the user click, after the library loads. Only `drive.file` is requested, with incremental grant inclusion off; account identity comes from Drive's `about` endpoint, without extra email/profile scopes. Tokens are stored only after permission and account checks pass. Closing the popup, denying permission, an account lookup failure or a superseded request retains the old connection. Reconnecting removes an older staged token so reload cannot undo it. Firefox's sandbox uses `cloneInto` for the GIS configuration callbacks.

The public OAuth web client ID is in `ST_GOOGLE_KEY`. Register each supported MusicBrainz origin (`https://musicbrainz.org`, `https://beta.musicbrainz.org`, `https://test.musicbrainz.org`) under Authorized JavaScript origins and enable Drive API. The registered `https://musicbrainz.org/?st-google=callback` redirect is reserved; the GIS popup token model does not redirect there. No client secret or refresh token is shipped. Expired sessions stop requests and require a user-driven reconnect, as Google requires for browser token renewal. The app's current Testing audience admits only registered test users; publishing and branding are controlled in Google Cloud.

Google files use a visible String Theory folder and private `stSuite`/`stKind` app properties. The library's authenticated request layer handles metadata and downloads; resumable uploads cover the shared 10 MB limit. Downloads use exact `headRevisionId` content revisions. The adapter does not rely on an undocumented compare-and-swap contract for Drive media updates: each sync change creates an immutable JSON revision, with parent IDs in its description. Listing follows all pages. Concurrent heads merge against all maximal common ancestors, recursively combining criss-cross merge bases so removed stars do not return. Concurrent same-field changes use a deterministic modified-time/ID order; this device's conflicts with the resulting remote snapshot still use the selected conflict policy. Sync history is retained and must not be manually removed; missing or cyclic ancestry stops sync before touching local data. Only heads and needed merge bases are downloaded.

Google backups are separate `backup` files, listed by their app properties. Apply validates ownership/type and downloads the listed content revision. Delete rechecks the listed content revision and moves the file to Trash, never permanently deletes it. Drive's general `version` includes invisible metadata changes and is unsuitable for this check: the live backup read-back changed that version without changing content. Switching providers preserves separate auth, state and baselines: Dropbox keeps its legacy keys, Google uses `string_theory.sync.google.auth`, `.state` and `.base`. Google `.state`, `.base` and pending `.oauth` are excluded from portable snapshots; credentials remain included. The selected provider is part of the shared sync settings.

[`sync-policy.js`](sync-policy.js) is the exclusion list, applied on export and import, including nested fields in JSON strings. All other GM values in the bundle are included, credentials too. Only suite-owned localStorage namespaces qualify; values stay partitioned by MusicBrainz origin. IndexedDB and sessionStorage contain caches and transient state and are excluded. Add an exclusion here whenever a script gains device state, a cache or temporary workflow data. Cache keys include `pc:mbdata:*`, `pc:cache:*`, `apollo:discogs-link-cache-v1` and `ch:ls-pruned`; a cache's settings, such as `ii:match_cache_days`, remain portable. Reading older backups filters them too; Sync and Push rewrite an older remote snapshot to remove excluded entries even if portable values are unchanged. Pull never writes remotely.

Sync creates the first remote file from local portable data when no file exists. Push replaces portable GM data and the current origin's localStorage; other origins are retained remotely, with no downloaded changes staged locally. Pull stages the remote portable snapshot as the source of truth while preserving edits made during the request and excluded device fields; a missing file is a no-op and retains the old baseline. All uploads retain the revision precondition. Explicit Pull retains a recovery copy before applying changes on reload.

Remote backups live in `/backups/string-theory-<ISO timestamp>-<UUID>.json` inside the same Dropbox app folder. Each save uses add mode with strict conflict checking and never changes `/string-theory.json` or the sync baseline. Listing follows every `list_folder/continue` cursor and accepts only backup files directly inside this folder. Applying downloads the selected file ID and exact listed revision, validates and filters the document, and uses the same merge/stage/recovery path as local Import. Deletion uses the selected file ID plus `parent_rev`, so a stale list cannot delete a changed file. The list and its confirmation state stay in memory; disconnect or an account change clears them. No new Dropbox scopes are needed.

[`sync-data.js`](sync-data.js) validates version 1 JSON snapshots and merges against the last successful remote baseline. Objects merge by field; ordered arrays remain atomic. EH stars merge by entity key, so removal on one device and addition on another both survive. The chosen conflict policy resolves same-field changes; first sync unions saved items. [`sync-storage.js`](sync-storage.js) preserves excluded local fields when applying portable data. The bundle gives each member a GM read/write guard which merges against the value that member read, preserving independent changes from other tabs.

Downloads are staged, never applied over a running editor. On the next MusicBrainz page load, pending changes merge with edits made since staging and apply before themes and members initialize. Another origin's localStorage remains in the snapshot until a page on that origin handles it. A recovery copy is retained before staging. The local bookkeeping keys are `string_theory.sync.state`, `.base`, `.stage` and `.recovery`; `.auth` and `.settings` are portable. Connection credentials are committed locally only after authorization and account lookup succeed. A different Dropbox account resets the old baseline. Web Locks coordinates tabs on the same origin; Dropbox's revision preconditions protect concurrent origins and devices. Failures retain local data and baseline and retry with backoff; automatic sync is off initially.
